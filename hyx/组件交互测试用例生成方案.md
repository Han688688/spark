# 组件交互测试用例自动生成方案

## 方案理念

**核心思想**: 从"API全覆盖"转向"基于交互场景的智能泛化"

```
传统方案: API全覆盖 → 1000+用例 → 维护困难
本方案: 交互描述 + 种子用例 → 智能泛化 → 高质量精简用例
```

## 一、Skill架构设计

### 1.1 Skill定义

**名称**: `TestCaseGenerationSkill`

**定位**: 通用的测试用例生成Skill，适用于多组件交互场景

**输入**:
```json
{
  "interaction_description": "文本描述的组件交互过程",
  "seed_cases": "已有的高质量测试用例脚本",
  "generation_config": "生成配置（模板、限制、策略）",
  "domain_knowledge": "领域知识（可选）"
}
```

**输出**:
```json
{
  "test_cases": "生成的测试用例列表",
  "automation_scripts": "自动化测试脚本",
  "coverage_analysis": "场景覆盖率分析",
  "quality_metrics": "用例质量指标"
}
```

### 1.2 Skill通用性设计

**为什么可以通用？**

1. **组件无关** - Skill不依赖特定组件，只关注交互模式
2. **模板驱动** - 通过模板适配不同场景
3. **种子学习** - 从已有用例学习，而非硬编码知识
4. **配置化** - 通过配置控制生成策略

**适用场景**:
- Spark + Kafka + HDFS
- Flink + Kafka + Iceberg  
- Spark + Hive + HBase
- 任意组件组合

## 二、组件交互描述格式

### 2.1 标准描述模板

**模板格式**:

```yaml
interaction:
  name: "数据流处理管道"
  components: [Kafka, Spark, HDFS]
  
  flow:
    - step: "数据采集"
      component: "Kafka"
      action: "Producer发送消息到Topic"
      input: "业务数据JSON"
      output: "Kafka消息队列"
      
    - step: "数据处理"
      component: "Spark"
      action: "Streaming消费Kafka数据"
      input: "Kafka Topic"
      output: "处理后DataFrame"
      
    - step: "数据存储"
      component: "HDFS"
      action: "DataFrame写入HDFS"
      input: "处理后数据"
      output: "HDFS文件"
  
  data_schema:
    kafka_message: {id: int, name: string, timestamp: long}
    spark_output: {id: int, processed_name: string, create_time: timestamp}
    hdfs_file_format: "Parquet"
  
  constraints:
    - "消息不能重复消费"
    - "文件写入需要保证完整性"
    - "异常需要重试机制"
```

### 2.2 交互类型分类

| 交互类型 | 描述 | 示例 |
|----------|------|------|
| **数据流** | 数据从一个组件流向另一个 | Kafka → Spark → HDFS |
| **状态同步** | 多组件状态需要一致 | Spark写入Hive + HBase同步 |
| **事件触发** | 一个组件事件触发另一个动作 | HDFS文件创建触发Spark处理 |
| **查询访问** | 一个组件查询另一个数据 | Spark查询Hive表 + HBase表 |
| **配置联动** | 配置变更影响多个组件 | Kafka Topic变更影响Spark订阅 |

## 三、用例生成模板

### 3.1 用例模板结构

**必填字段**:
```yaml
test_case_template:
  case_id: "auto-generated-{timestamp}-{index}"
  case_name: "{场景描述}"
  priority: "{P0/P1/P2}"
  
  scenario:
    description: "{交互场景描述}"
    components: [{组件列表}]
    interaction_type: "{数据流/状态同步/事件触发/查询访问/配置联动}"
  
  preconditions:
    - "{前置条件1}"
    - "{前置条件2}"
  
  test_steps:
    - step: 1
      action: "{操作动作}"
      component: "{执行组件}"
      expected_result: "{预期结果}"
  
  test_data:
    input: "{输入数据描述}"
    expected_output: "{预期输出数据}"
  
  assertions:
    - "{验证点1}"
    - "{验证点2}"
  
  cleanup:
    - "{清理动作}"
```

### 3.2 生成限制规则

**限制规则**:
```yaml
generation_limits:
  
  # 数量限制
  max_cases_per_scenario: 10  # 每个场景最多生成10个用例
  min_cases_per_scenario: 3   # 每个场景最少生成3个用例
  
  # 优先级分布
  priority_distribution:
    P0: 20%  # 核心路径
    P1: 50%  # 重要场景
    P2: 30%  # 边界场景
  
  # 覆盖维度（必选）
  required_coverage:
    - normal_flow     # 正常流程
    - error_handling  # 异常处理
    - boundary_values # 边界值
  
  # 可选覆盖（根据配置）
  optional_coverage:
    - performance     # 性能场景
    - concurrency     # 并发场景
    - security        # 安全场景
  
  # 数据限制
  data_limits:
    max_input_size: 10000  # 输入数据最大条数
    min_input_size: 1      # 输入数据最小条数
    allowed_types: [int, string, long, double, boolean, array, object]
  
  # 禁止生成
  forbidden_patterns:
    - "空用例（无验证点）"
    - "重复用例（完全相同）"
    - "无效数据（格式不匹配）"
    - "不可执行步骤（组件不支持）"
```

## 四、种子用例学习机制

### 4.1 种子用例分析

**从种子用例提取**:

```python
def analyze_seed_case(seed_case):
    """分析种子用例，提取关键特征"""
    
    features = {
        # 1. 交互模式
        'interaction_pattern': extract_interaction_pattern(seed_case),
        
        # 2. 数据特征
        'data_pattern': {
            'input_type': extract_input_type(seed_case),
            'output_type': extract_output_type(seed_case),
            'transform': extract_transform_logic(seed_case)
        },
        
        # 3. 验证模式
        'assertion_pattern': extract_assertions(seed_case),
        
        # 4. 异常处理模式
        'error_handling': extract_error_handling(seed_case),
        
        # 5. 清理模式
        'cleanup_pattern': extract_cleanup(seed_case)
    }
    
    return features
```

### 4.2 泛化生成策略

**泛化策略**:

| 策略 | 描述 | 示例 |
|------|------|------|
| **参数泛化** | 改变输入参数值 | 正常数据 → 边界值 → 异常数据 |
| **路径泛化** | 改变执行路径 | 正常路径 → 异常路径 → 回退路径 |
| **顺序泛化** | 改变操作顺序 | A→B→C → A→C→B → B→A→C |
| **组合泛化** | 组合多个场景 | 单一场景 → 组合场景 |
| **环境泛化** | 改变环境配置 | 默认配置 → 自定义配置 → 极限配置 |

### 5.1 脚本模板结构

**Python pytest模板**:

```python

import pytest
from components import {组件导入}

class Test{ScenarioName}:
    """{场景描述}"""
    
    @pytest.fixture
    def setup(self):
        """前置条件准备"""
        # {setup_code_from_seed}
        yield
        # {cleanup_code_from_seed}
    
    @pytest.mark.parametrize("test_data", [
        {generated_test_data_1},
        {generated_test_data_2},
        {generated_test_data_3}
    ])
    def test_{case_name}(self, setup, test_data):
        """{用例描述}"""
        
        # Step 1: {action_1}
        result_1 = {component}.{action}(test_data['input'])
        assert {assertion_1}
        
        # Step 2: {action_2}
        result_2 = {component}.{action}(result_1)
        assert {assertion_2}
        
        # Verify final output
        assert {final_assertion}
    
    def test_{case_name}_error(self):
        """异常场景测试"""
        # {error_handling_code_from_seed}
        with pytest.raises({expected_exception}):
            {error_action}
```

### 5.2 脚本生成规则

**生成规则**:
```yaml
script_generation_rules:
  
  # 框架选择
  framework: "pytest"  # 或 junit/testng
  
  # 命名规范
  naming:
    class_name: "Test{ScenarioName}"
    method_name: "test_{CaseName}"
    file_name: "test_{module}_{scenario}.py"
  
  # 结构规范
  structure:
    - class_docstring: "必填，描述场景"
    - setup_fixture: "必填，准备环境"
    - parametrize: "可选，数据驱动"
    - teardown: "必填，清理环境"
  
  # 断言规范
  assertions:
    - each_step_assertion: "每个步骤需有断言"
    - final_assertion: "最终结果断言"
    - error_assertion: "异常断言"
  
  # 数据驱动
  data_driven:
    min_parametrize_cases: 3
    max_parametrize_cases: 10
    data_format: "JSON/YAML/CSV"
```

## 六、Skill实现流程

### 6.1 生成流程

```
输入: 交互描述 + 种子用例 + 生成配置

Step 1: 解析交互描述
  → 提取组件列表
  → 提取交互步骤
  → 提取数据Schema
  → 提取约束条件

Step 2: 分析种子用例
  → 提取交互模式
  → 提取数据模式
  → 提取验证模式
  → 提取异常处理

Step 3: 应用生成模板
  → 选择合适的模板
  → 应用生成限制
  → 确保必选覆盖
  → 控制数量分布

Step 4: 执行泛化策略
  → 参数泛化（输入数据变体）
  → 路径泛化（正常/异常/边界）
  → 组合泛化（场景组合）

Step 5: 生成测试用例
  → 填充用例模板
  → 添加验证点
  → 添加清理步骤
  → 验证可执行性

Step 6: 生成自动化脚本
  → 选择脚本框架
  → 生成测试代码
  → 生成测试数据
  → 添加断言

Step 7: 质量检查
  → 检查用例完整性
  → 检查脚本可执行性
  → 检查覆盖维度
  → 计算质量指标

输出: 测试用例列表 + 自动化脚本 + 覆盖分析
```

## 七、Skill可用性评估

### 7.1 可用性指标

| 指标 | 预期值 | 评估 |
|------|--------|------|
| **用例有效性** | >80% | 生成的用例可执行 |
| **覆盖完整性** | >90% | 覆盖必选维度 |
| **重复率** | <5% | 避免重复用例 |
| **可维护性** | 高 | 模板化、标准化 |
| **泛化质量** | 中-高 | 依赖种子质量 |

### 7.2 适用场景评估

| 场景 | 适用性 | 说明 |
|------|--------|------|
| **组件交互测试** | ⭐⭐⭐⭐⭐ | 核心场景，最佳适用 |
| **新场景扩展** | ⭐⭐⭐⭐ | 基于种子泛化新场景 |
| **边界测试** | ⭐⭐⭐⭐ | 可生成边界值用例 |
| **异常测试** | ⭐⭐⭐ | 需要种子包含异常处理 |
| **性能测试** | ⭐⭐ | 不适用，需专门设计 |
| **API全覆盖** | ⭐ | 不适用，方案不支持 |

### 7.3 优势与局限

**优势**:
1. ✅ 通用性强 - 适用于任意组件组合
2. ✅ 质量可控 - 通过模板和限制控制
3. ✅ 效率高 - 聚焦关键场景而非全量覆盖
4. ✅ 可复用 - 种子用例可持续积累
5. ✅ 易维护 - 模板化生成，易于修改

**局限**:
1. ⚠️ 依赖种子质量 - 种子差则生成差
2. ⚠️ 不适合全量覆盖 - 聚焦关键路径
3. ⚠️ 异常场景有限 - 需要种子包含异常处理
4. ⚠️ 不支持性能测试 - 需要专门方案

## 九、实施建议

### 9.1 分阶段实施

**阶段1: 种子积累（1-2周）**
- 手工编写3-5个高质量种子用例
- 包含正常、异常、边界场景
- 建立用例模板规范

**阶段2: Skill开发（1周）**
- 实现交互描述解析
- 实现种子用例分析
- 实现泛化生成逻辑
- 实现脚本生成

**阶段3: 验证优化（1-2周）**
- 验证生成用例可执行性
- 调整生成限制参数
- 补充种子用例
- 优化泛化策略

**阶段4: 生产应用**
- 应用到实际测试项目
- 持续积累种子用例
- 持续优化模板

### 9.2 成功关键因素

1. **高质量种子用例** - 至少3个不同类型
2. **清晰的交互描述** - 标准化的描述模板
3. **合理的生成限制** - 平衡质量与数量
4. **持续迭代优化** - 积累种子，优化模板
