## 三大核心能力

### 1. 插件化架构

每个能力都是插件，可以独立扩展：

**分析插件 (AnalyzerPlugin)**：
- `static_code_analyzer` - 静态代码分析（提取调用链、数据流）
- `config_dependency_analyzer` - 配置依赖分析
- `api_doc_analyzer` - API文档分析

**生成插件 (GeneratorPlugin)**：
- `llm_generator` - LLM测试生成
- `data_driven_generator` - 数据驱动测试生成

**扩展方式**：
```python
from framework import AnalyzerPlugin

class MyAnalyzer(AnalyzerPlugin):
    @property
    def name(self):
        return "my_analyzer"
    
    def analyze(self, project_root, config):
        # 你的分析逻辑
        return {"my_data": "..."}
```

### 2. 多策略识别

不同类型的场景使用不同策略：

| 策略类别 | 策略名称 | 识别方式 | 适用场景 |
|---------|---------|---------|---------|
| interaction | interaction_discoverer | 调用链分析 | 组件交互场景 |
| interaction | log_based_discoverer | 日志分析 | 实际运行场景 |
| exception | bug_history_discoverer | 历史缺陷 | 回归测试 |
| performance | performance_discoverer | API+频率 | 性能测试 |

**交互场景识别原理**：

```
步骤1: 静态代码分析
├── 提取调用链 (ComponentA.methodA -> ComponentB.methodB)
├── 识别数据流 (参数传递、返回值处理)
└── 提取API定义

步骤2: 交互识别
├── 从调用链识别跨组件调用
├── 从配置识别连接关系
├── 从日志提取实际交互
└── 从API识别接口交互

步骤3: 场景生成
├── 正常交互场景
├── 异常交互场景（网络故障、组件异常）
├── 边界交互场景（数据边界、频率边界）
└── 并发交互场景
```

**示例：Spark与Hive交互**：

```python
# 识别的交互
Interaction(
    source="Spark",
    target="Hive",
    interaction_type="call",
    interface="SparkSession.sql(query)",
    frequency=100,
    critical_path=True
)

# 生成的场景
场景1: Spark SQL查询Hive表 (正常)
场景2: Hive元数据不可用 (异常)
场景3: 超大表查询 (边界)
场景4: 并发查询多个表 (并发)
```

### 3. 工作流编排

可自定义测试生成流程：

```yaml
workflows:
  my_workflow:
    steps:
      - name: analyze_code        # 步骤1: 分析代码
        type: analyze
        plugin: static_code_analyzer
      
      - name: discover_interaction  # 步骤2: 发现交互
        type: discover
        strategy_category: interaction
      
      - name: generate_tests       # 步骤3: 生成测试
        type: generate
        plugin: llm_generator
        priority: P0
```

## 快速开始

### 1. 基本使用

```bash
# 初始化
python hyx/framework.py init

# 查看能力
python hyx/framework.py list

# 运行默认工作流
python hyx/framework.py run

# 运行指定工作流
python hyx/framework.py run --workflow full

# 只生成P0场景
python hyx/framework.py run --workflow default --priority P0
```

### 2. 自定义插件

```bash
# 1. 创建插件文件
mkdir -p hyx/plugins

# 2. 编写插件
vi hyx/plugins/my_plugin.py
```

```python
# my_plugin.py

class MyStrategy(DiscovererStrategy):
    @property
    def name(self):
        return "my_strategy"
    
    def discover(self, context):
        # 你的发现逻辑
        scenarios = []
        # ...
        return scenarios
    
    def get_interactions(self, context):
        # 你的交互识别逻辑
        return []
```

```python
# 3. 注册插件

from my_plugin import MyStrategy

framework = TestAutomationFramework()

# 4. 运行

```

```python

    "name": "my_custom_workflow",
    "steps": [
        {"name": "analyze", "type": "analyze", "plugin": "static_code_analyzer"},
        {"name": "discover", "type": "discover", "strategy_category": "interaction"},
        {"name": "generate", "type": "generate", "plugin": "llm_generator"}
    ]
})

# 运行
framework.run("my_flow")
```

## 交互场景识别详解

### 识别维度

**维度1：调用链分析**

```
从源码提取：
- ComponentA.methodX() 调用 ComponentB.methodY()
- 参数类型、返回类型
- 调用频率（静态分析）
```

**维度2：配置依赖**

```
从配置文件提取：
- database.url -> MySQL组件
- api.endpoint -> ExternalService组件
- kafka.brokers -> Kafka组件
```

**维度3：运行时日志**

```
从日志提取：
- [Spark] executing query from Hive
- [ServiceA] calling ServiceB.api()
- ERROR: ComponentX timeout when calling ComponentY
```

**维度4：API文档**

```
从Swagger/OpenAPI提取：
- /api/v1/users -> UserService
- POST /api/v1/orders -> OrderService
- 内部调用关系
```

### 生成的交互场景类型

每个识别到的交互会生成多种场景：

**类型1：正常交互**
```
场景：Spark SQL查询Hive表
步骤：
1. 创建SparkSession
2. 执行SQL查询
3. 验证结果
预期：查询成功返回数据
```

**类型2：异常交互**
```
场景：Hive Metastore不可用
步骤：
1. 关闭Hive Metastore
2. Spark尝试查询
3. 验证异常处理
预期：异常被正确处理，有错误提示
```

**类型3：数据边界**
```
场景：超大查询结果
步骤：
1. 准备1000万行数据表
2. 执行全表查询
3. 验证性能和内存
预期：查询完成，内存稳定
```

**类型4：并发交互**
```
场景：多个Spark作业并发查询
步骤：
1. 启动10个并发作业
2. 同时查询同一Hive表
3. 验证数据一致性
预期：无锁冲突，数据一致
```

**类型5：版本兼容**
```
场景：Spark与Hive版本兼容
步骤：
1. 测试不同版本组合
2. 验证SQL语法兼容
3. 验证数据格式兼容
预期：版本兼容正常
```

## 扩展指南

### 扩展分析能力

```python
class MyAnalyzer(AnalyzerPlugin):
    def analyze(self, project_root, config):
        # 实现你的分析逻辑
        
        # 示例：分析数据模型
        data_models = self._extract_data_models(project_root)
        
        return {
            "data_models": data_models,
            "my_analysis": "..."
        }
```

### 扩展发现策略

```python
class MyDiscoverer(DiscovererStrategy):
    def discover(self, context):
        scenarios = []
        
        # 使用context中的分析结果
        data_models = context.get("data_models", [])
        
        # 为每个数据模型生成场景
        for model in data_models:
            scenarios.append(self._create_scenario(model))
        
        return scenarios
    
    def get_interactions(self, context):
        interactions = []
        
        # 识别数据流转交互
        data_flows = context.get("data_flows", [])
        
        for flow in data_flows:
            interactions.append(Interaction(
                source=flow["source"],
                target=flow["target"],
                interaction_type="data_flow"
            ))
        
        return interactions
```

### 扩展生成能力

```python
class MyGenerator(GeneratorPlugin):
    def generate(self, scenario, context):
        # 实现你的生成逻辑
        
        # 示例：生成Mockito Mock测试
        code = self._generate_mockito_test(scenario, context)
        
        return code
```

## 最佳实践

### 1. 策略组合

```yaml
# 多策略组合识别
workflows:
  comprehensive:
    steps:
      - type: discover
        strategy_category: interaction    # 调用链识别
      
      - type: discover
        strategy_category: log            # 日志识别
      
      - type: discover
        strategy_category: exception      # 历史缺陷
      
      - type: discover
        strategy_category: performance    # 性能场景
```

### 2. 渐进式生成

```yaml
# 先核心，再扩展
workflows:
  progressive:
    steps:
      - type: generate
        plugin: llm_generator
        priority: P0      # 第1批：核心路径
      
      - type: generate  
        plugin: llm_generator
        priority: P1      # 第2批：重要场景
      
      - type: generate
        plugin: data_driven_generator
        type: boundary    # 第3批：边界场景
```

### 3. 持续更新

```python
# 定期更新场景库
def update_scenarios():
    framework = TestAutomationFramework()
    
    # 1. 重新分析（代码变更）
    framework.run("default")
    
    # 2. 从新日志发现场景
    framework.run("interaction_focus", {
        "log_files": ["logs/latest.log"]
    })
    
    # 3. 从新缺陷发现场景
    framework.run("exception", {
        "bug_history_files": ["bugs/new_bugs.json"]
    })
```

## 与原方案对比

| 对比项 | 原方案(agent.py) | 新方案(framework.py) |
|-------|-----------------|---------------------|
| 架构 | 硬编码流程 | 插件化+可配置 |
| 扩展性 | 低，需改代码 | 高，添加插件即可 |
| 交互识别 | 仅基于项目信息 | 多维度多策略 |
| 工作流 | 固定流程 | 可自定义编排 |
| 维护成本 | 高 | 低（配置驱动） |

## 总结

**核心优势**：
1. **高扩展性** - 插件机制，无限扩展
2. **多策略识别** - 不同维度识别交互
3. **工作流编排** - 自定义流程
4. **配置驱动** - 无需改代码

**适用场景**：
- 多组件交互复杂的项目
- 需要持续扩展能力
- 团队协作（每个人贡献插件）
- 不同项目复用（配置适配）
